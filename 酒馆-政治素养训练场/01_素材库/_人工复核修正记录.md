## 逐条修正

### P-11《我人生中的第一笔回扣》 A(4) → B(3.2)

- 文件：`cards/procurement_depth.json`
- 原结算：`other_net = 0`，`main = 4`，等级 **A**
- 问题：卡片自己在 `outcome.others` 里写明——"2004 年那位台湾公司联络人因为看到一张发票被辞退，是这条链上唯一被真实惩罚的人，且她与回扣本身毫无关系"。**这正是一条 R7 情形（损害无关联第三方），却被记为 0。**
- 修正：`other_net` 0 → **−1**，`main` 4 → **3.2**，等级 A → **B**
- 备注：这张卡是全批唯一拿到 A 的卡，且是一张"吃回扣赚到了钱"的卡。修正后它仍然是全批最高分之一——这说明 **R8（灰色利益如实入账，只做风险定价）确实会让"灰色但干净收场"的路径得高分**，这是标准有意为之，不是漏洞。但"有人因此丢工作"必须扣回来。

### S-09《空降关系户顶了我的位子》 B(3.4) → C(1.8)

- 文件：`cards/sales.json`
- 原结算：`other_net = 3`（其中"公司止住客户情报外流"记 +2、"客户续约"记 +1）
- 问题：**公司不是自然人**。按 R12，组织受益不计入他人轴。
- 修正：`other_net` 3 → **1**（只保留客户续约），`main` 3.4 → **1.8**，等级 B → **C**
- 备注：这张卡本身 `fidelity = 疑似虚构`（搜狐故事号），结算精度本来就有限。修正后它落回 C（没输），与"位子拿回来了，但手段留下的瑕疵是暗伤"的定性更一致。

### P-04《抢来的主导权成了烫手山芋》 B(2.3) → C(1.5)

- 文件：`cards/procurement.json`
- 原结算：`other_net = 1`（"生产部拿回组长身份与绩效归属""财务保住降本预算""总经理保住面子"）
- 问题：三项全是**部门与个人职位的组织侧收益**。按 R12 不计入他人轴。
- 修正：`other_net` 1 → **0**，`main` 2.3 → **1.5**，等级 B → **C**
- 备注：这张卡原本就是子代理自己标记为"最不确定"的一张（采购席位 vs 财务视角），修正后更保守是合理的。

### P-03《30万摆桌上，我还是甲方吗》 C(1.3) → C(0.5)

- 文件：`cards/procurement.json`
- 原结算：`other_net = 1`（"现任供应商的份额保住了"——供应商是企业）
- 修正：`other_net` 1 → **0**，`main` 1.3 → **0.5**，等级仍为 **C**

## 二、证据（evidence）修正（2 张）

这两张卡的 evidence 句子**确实逐字存在于语料中**，但取自**另一篇文章**。第一版校验（全文语料子串匹配）发现不了，改成按来源 URL 分桶后暴露。

### E-01《背锅三个月换来绩效合格》

- 文件：`cards/engineer.json`
- 问题：`evidence[0]` 与 `evidence[1]` 是同一条重复的句子（"分享一下自己的背锅经历吧，刚毕业做的上位机软开……"），而这句话出自**另一篇**文章——`question/472569527`（即 E-03《leader 是股东》的来源），不是本卡的来源 `zhuanlan.zhihu.com/p/2082738151295136395`。
- 修正：替换为本卡自己来源里的两段原文——
  - "组里突然砸下来个新项目，全公司没一个人摸过流程，没人敢接。最后这活就顺理成章落到我头上了。……但全组人都知道，我是最不会拒绝的那个。"
  - "就这么跑了三个月，没人说我突然变凶变难说话，但是我自己的核心任务进度条，终于再也没掉过队。"

### E-07《离职埋雷，判了四年》

- 文件：`cards/engineer.json`
- 问题：有一项 evidence 是"这篇文章不讲虚的，只说我在真实冲突里用出来的 5 个方法"，出自《46 岁，我不背这个锅》（E-06 的来源），不属于本卡的腾讯云文章。
- 修正：把该卡 evidence 重置为本卡来源（腾讯云 · 伊顿公司 Davis Lu 案）自身的三段原文——交出电脑当天终止开关被触发、法庭文件里的数十万美元损失、以及 4 年监禁加 3 年监外监管的判决结果。
- **过程中我自己犯过一次错**：脚本里按 1-based 的显示序号去改 0-based 的数组，结果覆盖掉了一条本来正确的 evidence。改完必须重新跑校验，这一步不能省。

### 为什么这两处值得单独记

它们说明：**"evidence 全部命中"这个结论，取决于校验器问的是什么问题。**
- 问"这句话在语料库里存在吗" → 两处都会放行（它们的确存在，只是在别的文章里）；
- 问"这句话在这张卡自己的来源里吗" → 才会暴露。

同一份证据，换一个可信度更高的问法，结论就从 68/68 变成 66/68。

## 三、文件修复（1 个）

### `cards/engineer.json` JSON 语法错误

- 现象：`ConvertFrom-Json` 在第 14042 字符处失败，整份文件无法读取。
- 根因：E-02 的 `evidence` 里含**未转义的英文双引号**（原文是 `在代码注释里写了一句"fuck this place"`，以及 `"顾问费。一小时三千。预付。"啪。挂了。`）。这在 JSON 里会提前结束字符串。
- 修复：`tools/repair_json.ps1` —— 只对「整行就是一个 JSON 字符串」的行转义内部引号，带 `": "` 的键值行一律跳过。
- 首次修复用错了正则（把 `"key": "value"` 行的结构引号也转义了，文件被写坏）；已先整体回滚再重做，现文件合法、11 张卡齐全。
- 教训：**并发生成的结构化文件必须先做语法门槛校验再合并**，否则一个失败的文件会静默地让整批统计少一截（当时统计从 53 掉到 47，就是这份文件被跳过导致的）。

## 这次复核暴露出的标准问题

1. **"他人轴"必须有主体限定。** 这是 v1.1 新增 R12 的直接原因。不加限定，"公司受益"会被反复算成个人政治成就。
2. **"本局边界"必须开局声明。** 这是 v1.1 新增 R11 的直接原因。不加限定，"跳槽后变好了"会被算成"我赢了这场斗争"。
3. **方法型卡片的天花板需要统一。** 目前子代理的处理不一致：有的给 `null`，有的给 C。建议 v1.2 明确：**方法型卡片 `proxy_score` 一律为 `null`**（没有真实结局就没有结算），把 C 留给"有真实结局的止损型"。
